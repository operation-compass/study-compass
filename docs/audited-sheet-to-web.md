# 監査済みシート → Web自動公開（追加AI APIなし）

## 現在の有効化状態

`data/publishing/auto-publication.json` の enabled=true。2026-10-17、隔離環境7ケースの成功、本番の新規バッチ公開・障害復旧の未実証、Cloudflare標準プレビューの失敗が残ることを説明したうえで、ユーザーが「自動公開の有効化を承認する」と明示承認。承認範囲は同日のactivation-approval.jsonに記録する。監査条件・最大5問・正本照合・実証拠照合・同時更新時停止の条件は緩和しない。

## 対象と利用方法

運用変更時は `../AGENTS.md` の固定ルールも参照する。2026-10-18、既存クラウド定期タスクの指示を `scheduled-content-audit-prompt.md` の内容へ更新・保存確認済み。定期タスクは内容監査と証拠保存を担当し、GASは認証同期を担当する。設定保存だけで独立監査の実行能力や無人完走を実証したとは扱わない。初期5問の本番公開は実証済みだが、更新後の定期タスクの無人3監査完了は次回実行での確認が必要。実障害時の復旧は未実証。

正本の問題MASTERに登録された問題のうち、既存の3段階監査ログで同一ID・version・SHA v2の正確性／教材品質／技術がPASS、LOW、例外なし、READYになったものだけを対象とする。問題を追加しただけ、PUBLIC/TRUEにしただけ、READYという文字だけでは公開しない。監査済みの問題を投入する運用であり、AI内容監査をAPIで自動実行する機能は使用しない。

監査のMD証拠本文とJSONレビュー記録を作業ブランチの `docs/audits/` に保存する。P列の各レビューの `evidence_file` と `evidence_sha256` が実ファイルに一致し、同じID・version・role・reviewer・日時・問題SHAを持つJSON記録が必要。従来の実監査済み2問の形式と互換。Sheetsに証拠のないPASSだけを記入しても公開できない。

## 自動経路

1. 既存GASトリガーが認証済み正本と監査ログを読み、未掲載差分から最大5問を原子的に同期。
2. 既存の自動提案処理が、現在のmainを基に差分・既存問題・履歴・学習画面構造を検査してPRを作成。差分ゼロなら何もしない。
3. mainに置いた自動公開ワークフローが、成功した提案処理を契機に実行。作業ブランチのコードは実行せず、データと証拠だけを読む。
4. GitHub上の同期元コミット・投稿者・変更ファイル・原本blobを照合。3監査の実ファイルSHAと対のJSON記録を再照合。24時間以内の認証済み同期が必要。
5. mainにある固定の公開エンジンでHTMLを再生成し、PRがその両HTMLだけに完全一致するか確認。最大5問。mainまたはstagingが進んだ場合は停止して次の処理を待つ。
6. 検証したPRについて、専用の `verify-publication-candidate.yml` を起動する。固定したmain・監査元・候補コミットを読み、mainのコードだけで証拠照合とHTML再生成を行い、候補差分・静的検査を確認する。該当リクエストのCI成功を待ち、mainと監査元を再確認してからマージする。失敗・別リクエストの成功・タイムアウトはマージしない。GitHubのトークンでのマージはpushワークフローを起動しない場合があるため、既存配信ワークフローを明示的に起動して完了を待つ。
7. 配信CIの3モード確認に加え、本番の問題集全体が期待するID・問題・選択肢・正答・解説と一致することを照合。実行結果と生成物は30日間のGitHub artifactへ保存。

## 失敗時

マージ前の失敗は本番を変更しない。マージ後の配信・問題照合に失敗した場合、mainがその公開コミットのままなら今回の2つのHTMLを直前状態へ戻す新規コミットを作り、復旧配信と問題集照合を実行する。force pushやmain全体のresetは行わない。後続のmain変更があれば自動復旧を止めて失敗記録を残し、別作業を上書きしない。

ローカルの隔離Git環境でファイル単位復旧と他ファイル保持をテストする。本番障害を意図的に発生させる実験は行わない。非空の新規監査済みバッチによる自動マージ〜障害時復旧の全経路は、実運用での確認前に「実証済み」と扱わない。

`test-auto-publication-controller.cjs` は実際の公開制御コード、ローカルのGitリポジトリ、過去の実監査済み2問の固定証拠を使用し、外部HTTPを閉じた模擬応答に置き換えて経路を検証する。公開無効、新規PR、既存下書き、配信内容不一致、配信失敗、マージ後の別作業、マージ瞬間の競合を対象とする。証拠の時刻はテスト内で過去の実行時刻を再現するだけで、監査の有効期限を更新せず、正本や実stagingには出力しない。これは非空バッチの制御経路の隔離検証であり、実GitHub権限や実Cloudflare障害の実証ではない。

## 保持するもの

既存問題のID・掲載順・学習履歴、オプチャテンプレート、LISTEN、他の定期タスク、既存GASトリガー。新しいAIキーや有料AI APIは不要。各サービスの既存利用枠・上限内で動作する設計であり、無制限無料を保証するものではない。

API監査基盤PR #14は別用途の下書きとして保留し、本経路には導入しない。

## 定期監査の成立条件と再開手順

クラウド定期タスクに指示を保存しても、独立した3実行やGitHub・Sheetsへの書き込み能力が追加されるわけではない。実行環境が3役割を独立して起動でき、実証拠保存・正本への限定書き込み・保存後照合まで行えることを実データで確認する。能力が不足する場合はPENDINGとし、同一実行に3名義を付けて代替しない。追加の有料AI接続は導入しない。

定期タスク自身を含む停止・再開・頻度変更・通知変更は、ユーザーの明示指示が必要。同じ阻害条件の反復は、未完了対象と前回拒否理由を保存し、変化だけを確認することで防ぐ。ツールの安全チェックに拒否された場合、操作・対象・拒否原文・未保存範囲・必要なユーザー対応を記録し、別経路で迂回しない。

証拠ファイルだけを修正しても提案ワークフローのpush条件には入らない。GASは同じ内容の同期を12時間未満では省略する。修正後は認証済み同期が24時間以内か、正本と証拠と同一版・SHAかを確認し、既存の自動公開ワークフローをmainから明示的に再実行する。同期が古ければ既存GASの正規同期を待つ。日時・認証元を手で更新せず、新規トリガーを作らない。

専用候補CIは内容監査や実画面での採点・スマホ・履歴確認を代替しない。静的検査、3モードDOM起動、本番データ一致、独立内容監査、実障害復旧をそれぞれ区別して報告する。
